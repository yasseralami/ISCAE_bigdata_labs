Cas d'étude : Pipeline AML temps-réel
25 min
À faire
CONTEXTE MÉTIER
Problème : Banque marocaine reçoit 500 transactions/sec. Doit détecter les opérations suspectes EN TEMPS-RÉEL.

Loi LCBFT : Lutte Contre le Blanchiment de Capitaux et le Financement du Terrorisme = obligation légale.

Enjeu : Non-respect = amendes massives + fermeture de compte.
OBJECTIFS
✅Comprendre Producer = simule 500 tx/sec
✅Comprendre Consumer = filtre AML 3 règles
✅Voir les données brutes → filtrées → alertées
✅Utiliser Kafka-UI pour monitoring production
🏗️ ARCHITECTURE KAFKA
Producer : Simule 500 tx/sec avec délai visible (100ms)
Topic : 3 partitions pour parallélisme
Consumer : Applique 3 règles AML (montant > 10k MAD, pays blacklist, fraude)
EOS : Exactly-Once Semantics = zéro doublon
QUIZ : Comprendre le concept
Q1: Pourquoi Kafka plutôt qu'une base de données ?
✅ Traite 500 msg/sec en temps-réel (BD trop lente)
❌ C'est plus cher
✅ Kafka = streaming haute-vitesse. BD = données historiques.
❌ Kafka traite les flux temps-réel 500+ msg/sec.
Q2: Rôle des 3 partitions ?
✅ Paralléliser : 3 consumers peuvent lire en même temps
❌ Stocker 3 copies
✅ Partitions = distribution/parallélisme.
❌ Replication factor fait les copies (ici=1).
Q3: EOS (Exactly-Once Semantics) ?
✅ Aucune transaction traitée deux fois
❌ Chaque message est dupliqué
✅ EOS = garantie zéro doublon. Essentiel pour la finance !
❌ EOS = opposite : zéro doublon.

Observer le LAG (très important !)
📊 Interprétation LAG
LAG = 0 ✅ Consumer à jour, zéro retard
LAG > 100 ❌ Consumer traîne, risque
LAG croissant ⚠️ Problème de performance
QUIZ Kafka-UI
Q1: LAG = 0 signifie ?
✅ Consumer a lu TOUS les messages (zéro retard)
❌ Le topic est vide
✅ LAG = 0 = parfait
❌ LAG = retard du consumer
